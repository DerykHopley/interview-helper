# The Unlock Key is separate from the Access Token

Two secrets exist and they are deliberately not the same thing. The **Access Token** is issued by the app owner, shared by a group, expires after 8 hours, and only lets the Worker spend the OpenRouter budget. The **Unlock Key** is generated by the app on a Candidate's first visit, shown once, never expires, and derives the key that encrypts that Candidate's stored data (AES-GCM via Web Crypto). Using the Access Token as the encryption secret was considered and rejected: stored data would become unreadable when the token expired, and everyone sharing a token would share a key.

## Consequences

- A lost Unlock Key means the Candidate's data cannot be recovered; the app says so at setup and asks them to save it in a password manager.
- Unreadable data can still be deleted: the unlock screen offers "Start over", which, after a typed confirmation, wipes all stored data and runs first-visit setup with a new Unlock Key. Anyone with access to the browser can do this, but cannot read the data.
- The unlock screen verifies the key before decrypting anything, so a wrong key gives a clear "that key doesn't match" message.
- The Unlock Key is app-generated rather than a chosen passphrase, so it cannot be weak.
- "Remember this browser" (keeping a non-extractable key in the browser) is a later addition, not a replacement.
